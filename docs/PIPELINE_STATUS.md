## `session_001` is not confirmed to match any defined task — read this before trusting any "verified against real data" claim below

**`session_001` is the only session anywhere in this repo** (`raw/`,
`processed/`, and the one delivered batch all contain exactly this one
session — confirmed 2026-07-06). Every "verified against real `session_001`
footage" claim in the sections below is real in the sense that the code
actually ran against actual video/IMU data and produced actual output — but
none of those claims should be read as confirmation that `session_001`
depicts `bolt_tightening` or any other specific entry in `TASK_SIGNATURES`.
It almost certainly does not.

**What the footage actually shows:** two independent real Claude vision
calls (§7, `claude-opus-4-8`, 2026-07-05) — not mocked, not hand-picked —
looking at real sampled frames from `session_001` both independently
described **paperwork sorting and stapling at a workbench** (documents from
a stack, a handheld stapler, sorting into folders), not bolt tightening or
any other task currently in `TASK_SIGNATURES`.

**No capture metadata confirms or contradicts this.** Checked: `raw/session_001/`
contains only `raw.mp4` and `imu.json`, no capture log or manifest.
`session_meta.json` has only technical capture parameters (fps, resolution,
codec) plus a pre-existing `consent_note` that already says this is an
*"Example/demo session shipped with this repo — simulated consent for
quickstart purposes, not a real worker's recorded consent."* `raw/session_001/`
is explicitly un-ignored in `.gitignore` (meant to be tracked) but
`git ls-files raw/` returns nothing — it was never actually committed, so
there's no commit history to check either. README.md calls it only "the
included example session," with no description of its content. **There is
no record anywhere in this repo of what task this footage was captured to
depict.** The likeliest explanation is that it's generic stock/placeholder
footage bundled for pipeline plumbing tests, not a real factory-floor
capture matching this project's taxonomy.

**Fixed as part of resolving this:** `07_task_classify.py`'s task-signature
scorer had a silent tie-breaking bug — when multiple tasks tied at the top
score, the winner was decided by dict-insertion-order in `TASK_SIGNATURES`,
not by genuine confidence. Against `session_001`'s real primitive counts,
**8 of the 9 defined tasks tie at a score of exactly 1.0** — the signatures
were loose enough that generic, varied manipulation activity trivially
saturated almost all of them. The old code picked `bolt_tightening` only
because it happens to come first in the dict, producing a confident-looking
but arbitrary label. Fixed: a tie within `TASK_TIE_MARGIN` (0.05, new
`config.py` constant) across ≥2 tasks now correctly falls back to
`"unknown"` + `needs_human_review: true`, the same fallback path used for a
low single-task score. With the fix, `07_task_classify.py` now correctly
returns `unknown` for `session_001` — which is very likely the right
answer, not a regression.

**Also fixed (2026-07-06), a separate but related discriminability bug:**
5 of the 9 `TASK_SIGNATURES` entries were defined by only 2 required
primitives (`material_transfer`, `box_seal`, `label_apply`,
`inspection_visual`, `packaging_fold`). Averaging 2 components means
satisfying just ONE of them — with the other completely absent — lands at
exactly 0.5, the classifier's confidence threshold. Confirmed empirically
with synthetic fixtures: `power_grasp=20` alone (zero transport at all)
confidently fired `material_transfer`; `lateral_pinch`/`idle`/`finger_curl`
alone did the same for their respective tasks. Fixed by giving every
signature ≥3 required primitives (see `config.TASK_SIGNATURES`'s inline
comment for the full rationale and the acknowledged residual limitation:
only 6 of 9 tasks have a genuinely task-exclusive anchor primitive — the
other 3 share their entire vocabulary with other tasks, an accepted
limitation of a 12-primitive vocabulary covering 9 tasks, not something a
threshold tweak fully resolves). **This fix was verified with SYNTHETIC
fixtures only** — `tests/test_task_classify.py`'s
`TestSyntheticSignatureDiscriminability` class, explicitly labeled as such
in its own docstring to avoid repeating the exact mistake that let
`session_001` pass as a real-data validation reference for as long as it
did. Synthetic tests confirm internal self-consistency of the signatures;
they say nothing about whether any signature fires correctly on real
footage of a worker actually performing that task — see the blocker above.

**Net effect on prior sections' verification claims:** every §1/§4/§6/§9/§10
claim of the form "verified the pipeline's plumbing/math/propagation against
real `session_001` data" still stands as written — those verified that code
paths run correctly against real files and produce internally consistent,
non-fabricated output. But any claim that could be read as "confirms
`bolt_tightening`'s primitive signature correctly fires on real matching
footage" cannot be supported by this session, because there is no evidence
this footage was ever meant to depict `bolt_tightening` (or any of the other
nine defined tasks) in the first place.

**Where this leaves `session_001` specifically:** it stays in the repo as a
genuinely valuable edge-case regression test — it now proves the classifier
correctly abstains with `unknown` on out-of-taxonomy footage instead of
confidently mislabeling it — but must **not** be treated as "the" reference
session for validating in-taxonomy behavior going forward. This blocks
meaningfully validating §1's IMU-strategy primitive detection, §6's
per-episode task classification, §9's confidence propagation, and §7's VLM
cross-check against a session where the "correct" answer is actually known
— all of that testing so far has necessarily used either synthetic fixtures
or this now-confirmed-ambiguous session. See the business-blocker banner at
the top of this section for the decision this actually needs — do not
resume building against unverified footage as if this were resolved.
